# 업무 종합 관리 — 파일 분리 구조

원본 `index.html` 하나(약 9,000줄)에 몰려있던 코드를, 내비게이션 독의 카테고리 기준으로
`css/`, `js/` 폴더 아래 파일별로 나눴습니다. **`index.html`은 이 파일들을 그대로 조합해서
만든 최종 결과물이며, 원본과 100% 동일하게 동작합니다** (분리 후 재조합한 내용을 원본과
한 글자도 다르지 않게 diff로 검증했습니다).

## CSS와 JS, 왜 각각 하나의 파일로 합쳤는지

- **JS**는 이 앱이 로그인 직후 Supabase 클라우드 동기화를 `await`으로 순서를 맞춰
  처리하고, 그 뒤를 이어 계정/할일/상담사/스케줄 등 각 페이지의 데이터를 순서대로
  불러오는 구조예요. 만약 `js/*.js` 파일들을 각각 독립된 `<script src>`로 따로
  불러오면 이 실행 순서가 깨져서 "동기화 전에 화면부터 그려지는" 등의 오류가 날 수
  있습니다. 그래서 `js/` 파일들은 **원래 순서 그대로 이어붙여 하나의 파일(`app.js`)로
  묶어서 실행**하도록 만들었고, 그 조합 작업을 `build.js`가 대신 해줍니다.
- **CSS**는 파일별로 완전히 독립적이라 원래는 각각 `<link>`로 따로 불러와도
  문제가 없었지만(그래서 예전엔 빌드 없이 새로고침만으로 반영됐습니다), 2026-09
  번들 최적화 작업 이후로는 CSS도 하나의 파일(`styles.min.css`)로 합치고
  압축해서 불러오도록 바꿨습니다. **그래서 지금은 CSS를 고쳐도 JS와 마찬가지로
  `node build.js`를 한 번 더 돌려야 반영됩니다** (아래 "사용 방법" 참고).

## 사용 방법

- **그냥 열기**: `index.html`을 열면 바로 원본과 동일하게 동작합니다. (다른 파일들과 폴더
  구조를 그대로 유지한 채로 옮기세요 — `css/`, `js/`, `tools/` 폴더와 `app.js`,
  `styles.min.css`가 `index.html`과 같은 위치에 있어야 합니다.)
- **코드를 수정하고 싶을 때**:
  1. 수정하려는 카테고리의 파일만 열어서 편집합니다. (예: 캘린더 관련 수정 → `js/02-calendar.js`, `css/04-calendar.css`)
  2. CSS든 JS든 고쳤다면, Node.js가 설치되어 있는 컴퓨터에서 이 폴더 안에 들어가
     아래 명령을 한 번 실행해서 `index.html` / `app.js` / `styles.min.css`를
     다시 만들어야 합니다.
     ```
     node build.js
     ```
     (Node.js가 없다면 저에게 다시 파일을 올려주시면 같은 방식으로 다시 조합해드릴게요.)

### 월별 스케줄 셀 복사/붙여넣기 (2026-09 추가)

- **복사**: 칸을 클릭하거나 드래그로 범위를 고른 뒤 `Ctrl+C`(Mac은 `⌘+C`). 상태와 **메모**가
  함께 복사되고, 복사한 칸은 점선 테두리로 표시됩니다(`Esc`로 점선만 끔). 범위를 드래그해
  뜬 "N칸 선택됨" 메뉴는 `Ctrl+C`를 누르면 자동으로 닫힙니다.
- **붙여넣기**: 붙여넣을 칸을 클릭한 뒤 `Ctrl+V` — 그 칸이 왼쪽 위 시작점이 됩니다. 1칸을
  복사했다면 여러 칸을 드래그로 골라 한 번에 채울 수도 있습니다. 붙여넣기는 **상태와 메모를
  함께 덮어쓰므로**, 복사한 칸에 메모가 없으면 붙여넣은 칸의 기존 메모는 지워집니다
  (결과 안내에 "기존 메모 N개 삭제됨"으로 표시). `Ctrl+Z` 한 번으로 통째로 되돌립니다.
  잠긴 달이 범위에 섞여 있으면 아무것도 바꾸지 않습니다.
- **엑셀 등에서 복사한 값**(`오프`·`연차`·`1` … 탭/줄바꿈 표)도 붙여넣을 수 있습니다. 이 경우
  메모 정보가 없으므로 상태만 바꾸고 기존 메모는 그대로 둡니다.
- 메모는 시스템 클립보드에 실을 수 없어서 앱 안 버퍼에 따로 보관합니다. 붙여넣을 때 클립보드
  텍스트가 복사할 때 넣어 둔 텍스트와 같을 때만 그 버퍼(메모 포함)를 쓰기 때문에, 그 사이 다른
  곳에서 복사한 내용이 있으면 옛 복사본이 엉뚱하게 붙지 않습니다.

### 테스트를 붙이면서 같이 고친 것 (2026-09)

- **`esc()`가 따옴표를 이스케이프하지 않던 문제** — 예전 구현은

  제목이나 스케줄 셀 메모에 큰따옴표가 하나만 들어가도 거기서 속성이 끊겨

## `node build.js` 깜빡하는 실수 막기 (자동 빌드)

CSS/JS를 고치고 `node build.js`를 깜빡하면 화면엔 반영 안 된 옛날 버전이 그대로
남습니다. 이걸 방지하는 두 가지 방법을 추가했습니다. 굳이 둘 다 안 써도 되고,
편한 쪽만 써도 됩니다.

### 방법 1. watch 모드 (작업 중 자동 빌드)

작업을 시작할 때 터미널에서 한 번만 실행해두면, `css/`나 `js/` 폴더의 파일을
저장할 때마다 자동으로 `node build.js`가 실행됩니다.

```
node tools/watch.js
```

(`npm install`을 했다면 `npm run watch` 로도 실행됩니다.) 켜둔 상태로 평소처럼
파일을 수정·저장하고, 새로고침해서 확인하면 됩니다. 종료하려면 터미널에서
Ctrl+C를 누르세요.

### 방법 2. git commit 훅 (커밋 시점에 자동 빌드 + 자동 포함)

이 프로젝트를 git으로 관리한다면, 커밋할 때마다 자동으로 빌드하고 결과물
(`index.html`, `app.js`, `styles.min.css`)을 그 커밋에 포함시켜주는 훅을
추가했습니다. `git init` 이후 아래 명령을 한 번만 실행하면 설치됩니다
(`npm install`을 하면 `postinstall` 스크립트로 자동 설치됩니다).

```
node tools/install-hooks.js
```

이후로는 `git commit`을 실행할 때마다 훅이 다음 순서로 돌아갑니다.

1. **`npm test`** — 테스트가 하나라도 실패하면 커밋을 막습니다(2026-09 추가).
   고쳐야 할 게 명확히 보이므로 되도록 고치고 커밋해주세요. 정말 급할 땐
   `git commit --no-verify`로 건너뛸 수 있습니다.
2. **`node build.js`** — 빌드가 실패해도 커밋을 막습니다.
3. 새로 생성된 빌드 결과물을 자동으로 `git add`해서 커밋에 포함시킵니다.

> 두 방법 모두 `build.js`의 로직 자체는 전혀 건드리지 않고, "언제 build.js를
> 실행하는가"만 자동화한 것입니다. 빌드 결과가 걱정되면 언제든 `node build.js`를
> 손으로 다시 실행해서 직접 확인해도 됩니다.

## 보안 업데이트 (2026-09): 계정 정보(비밀번호 해시·cloudAuthSecret) 노출 차단

로그인 화면에서 "아이디만 입력해도 계정 종류를 미리 보여주기" 위해 로그인 전(anon)에도
`personal-app:accounts` 한 줄을 읽을 수 있게 열어뒀는데, Supabase RLS는 행 단위로만
막을 수 있어서 그 한 줄 안에 있던 모든 계정의 비밀번호 해시·salt와 Supabase 로그인에
쓰이던 cloudAuthSecret까지 로그인 없이 통째로 읽을 수 있는 문제가 있었습니다.
cloudAuthSecret이 새어나가면 사람 비밀번호 없이도 그 값만으로 Supabase 인증을 통과해
전체 데이터(첨부파일 포함)에 접근할 수 있었습니다.

지금은:
- 로그인 화면은 더 이상 계정 목록을 직접 읽지 않고, 비밀번호 관련 값이 전혀 없는
  안전한 서버 함수(`get_login_bootstrap`, `get_login_account_info`)로만 필요한 정보를
  받습니다.
- 실제 비밀번호 확인·변경은 전부 새 Edge Function `auth-admin`(서비스 롤 키로만 동작)
  안에서 처리되고, 비밀번호 해시나 cloudAuthSecret은 이제 어디서도 브라우저로 나가지
  않습니다.
- cloudAuthSecret 자체를 더 이상 쓰지 않습니다 — 사람이 입력하는 비밀번호가 곧 실제
  Supabase Auth 비밀번호입니다. 예전 계정은 다음 로그인 한 번에 한해 서버가 비밀번호를
  확인하고 조용히 이 방식으로 전환해줍니다(사람이 따로 할 일은 없어요).

**아직 적용 전이라면 반드시 해야 할 일 (1회성, 순서 중요):**

1. `node build.js`로 다시 빌드해서 먼저 배포합니다(새 로그인 화면 코드가 먼저 떠
   있어야 합니다).
2. Edge Function을 배포합니다: `supabase functions deploy auth-admin`
3. `supabase/auth-lockdown-migration.sql`을 Supabase 대시보드 → SQL Editor에서
   실행합니다(안전한 RPC 함수를 만들고, 예전에 열어뒀던 anon 읽기 권한을 닫습니다).
4. 계정 하나(가능하면 테스트 계정)로 로그아웃 후 다시 로그인해서 잘 되는지 확인한
   뒤, 팀원들에게 다음 로그인부터는 평소처럼 하면 된다고 안내해주세요.

자세한 배경과 순서가 중요한 이유는 `supabase/auth-lockdown-migration.sql`과
`supabase/functions/auth-admin/index.ts` 상단 주석에 적어뒀습니다.

## 보안 강화 (2026-09): 서버(DB)에서 데이터 자체를 검증

지금까지 "QA 점수는 0~100 사이여야 한다", "잠긴 달의 점수는 못 고친다", "계정
목록은 배열이어야 한다" 같은 규칙은 전부 브라우저(js/05a-qa-data.js 등 QA 관련 파일)에만 있었습니다.
화면을 통해 저장할 때는 문제없지만, 로그인한 사람이 Supabase REST API를
개발자도구나 curl로 직접 두드리면 이 규칙을 전부 건너뛸 수 있었습니다(RLS는
"로그인했는가"만 볼 뿐, "이 값이 말이 되는가"는 보지 않습니다).

`supabase/kv-store-server-validation-migration.sql`을 적용하면, kv_store에
저장되기 직전에 서버(Postgres 트리거)가 직접 다음을 강제합니다:
- 저장하려는 값이 올바른 JSON인지, 크기가 4MB를 넘지 않는지
- QA 점수(`scores`)가 전부 0~100 사이의 숫자인지
- 이미 잠긴 달의 점수를 잠긴 채로 몰래 바꾸려는 시도인지
- 계정 목록(`personal-app:accounts`)이 배열 형태를 유지하는지, 통째로 빈
  배열로 덮어써지지 않는지

이 검증은 화면 저장이든, 부분 업데이트(`kv_apply_patch`)든, REST API 직접
호출이든 어떤 경로로 값이 들어와도 똑같이 적용됩니다. 정상적인 화면 사용
중에는 항상 이 규칙을 만족하는 값만 저장하므로 아무것도 달라지지 않고,
화면을 거치지 않은 비정상적인 쓰기만 서버에서 막힙니다.

다만 "누가 어떤 데이터를 고칠 권한이 있는가"(예: 팀원이 다른 사람 점수나
관리자 전용 설정을 고치는 것)까지는 막지 않습니다 — 이 앱은 로그인한 팀원
전체가 같은 데이터를 공유하는 구조라서, 그 부분까지 서버가 막으려면 계정별/
역할별로 데이터 접근을 나누는 더 큰 구조 변경이 필요합니다.

**아직 적용 전이라면 반드시 해야 할 일 (1회성):**

1. `supabase/kv-store-server-validation-migration.sql`을 Supabase 대시보드 →
   SQL Editor에서 실행합니다 (다른 마이그레이션과 순서 상관없이, 여러 번
   실행해도 안전합니다).
2. 클라이언트 코드 변경은 없으므로 `node build.js`를 다시 돌릴 필요는
   없습니다 — SQL만 실행하면 바로 적용됩니다.

## 새 기능 (2026-09): 업무 정리 메모에 파일 첨부

각 메모를 펼치면 내용 아래에 "첨부파일" 영역이 생겨서, 파일을 올려두고(여러 개
가능) 나중에 다시 다운로드할 수 있습니다. 파일 원본은 메모 JSON(kv_store)이 아니라
Supabase Storage의 별도 버킷에 저장되고, 메모에는 파일 이름/크기/저장 경로만
함께 동기화됩니다. 파일 1개당 최대 20MB까지 올릴 수 있습니다.

**아직 적용 전이라면 반드시 해야 할 일 (1회성):**

1. `supabase/notes-attachments-storage-setup.sql`을 Supabase 대시보드 → SQL
   Editor에서 실행합니다 (다른 마이그레이션과 순서 상관없이, 여러 번 실행해도
   안전합니다). 이 SQL이 첨부파일 저장용 비공개 버킷과 권한을 만듭니다.
2. `node build.js`로 다시 빌드해서 배포합니다.

이 SQL을 실행하기 전까지는 "파일 첨부" 버튼을 눌러도 업로드가 실패합니다(버킷이
없다는 안내가 뜹니다).

## 저장 최적화 (2026-09): 부분 업데이트(patch)

예전에는 QA·면담일지·월별 스케줄처럼 항목이 많은 카테고리에서 항목 하나(체크박스
하나, 텍스트 한 줄)만 고쳐도 그 카테고리 전체 JSON을 통째로 서버에 다시 보냈습니다.
지금은 "이전에 서버와 같았던 값"과 "지금 저장하려는 값"을 비교해서 바뀐 자리만
뽑아 서버에 그 자리만 patch하도록 바꿨습니다. 기존 항목의 id·순서가 그대로 유지된
채 내용만 바뀐 경우에만 patch가 적용되고, 항목을 새로 추가·삭제하거나 순서를
바꾸는 저장은 지금까지처럼 전체를 다시 보냅니다(그 정도 변경까지 patch로 표현하면
복잡도가 크게 늘어서 지금은 다루지 않았습니다).

**아직 적용 전이라면 반드시 해야 할 일 (1회성):**

1. `supabase/kv-patch-function.sql`을 Supabase 대시보드 → SQL Editor에서 실행합니다
   (`auth-rls-migration.sql`과 순서 상관없이, 여러 번 실행해도 안전합니다).
2. 이게 전부입니다 — 클라이언트는 이미 이 함수를 호출하도록 되어 있고, 함수가 아직
   없거나 호출이 실패해도 자동으로 예전처럼 "전체 저장"으로 되돌아가므로, 이 SQL을
   올리지 않아도 앱은 정상 동작합니다(이 최적화로 인한 절약만 못 받을 뿐).

## 성능 최적화 (2026-09): 번들 분리 + CSS 압축

예전에는 JS 전체(약 700KB)를 `index.html` 안에 `<script>` 블록으로 그대로
박아넣고 있었어요. 그러면 브라우저가 화면 뼈대를 그리기도 전에 이 큰 파일을
`index.html`의 일부로 매번 통째로 받아야 했고, 새로고침할 때마다 별도 파일처럼
캐시되지 못하고 매번 새로 받아야 했습니다. 지금은:

- JS는 `app.js`라는 별도 파일로 빼서 `<script src="app.js">`로 불러옵니다
  (내용은 한 글자도 안 바꿨고, 파일 위치만 옮겼습니다 — `js/` 폴더 24개 파일을
  원래 순서 그대로 이어붙인 것과 정확히 일치하는지 diff로 확인했습니다).
- CSS 13개 파일은 순서 그대로 합친 뒤 주석과 불필요한 공백만 제거해서
  `styles.min.css` 하나로 만듭니다 (문자열이나 `url(...)` 안의 내용은 절대
  건드리지 않습니다). 압축기(`tools/minify-css.js`)는 서로 다른 두 가지 방식으로
  구현한 결과가 완전히 일치하는 것으로 교차 검증했고, 압축 전후 코드에서 실제
  중괄호 개수가 정확히 일치하는지도 확인했습니다(주석 속에 예시로 적힌 중괄호
  1쌍만 주석째로 사라진 것까지 확인함). 압축 결과 CSS 용량은 약 24% 줄었습니다.
- 결과적으로 `index.html` 자체의 용량은 **약 720KB → 약 2KB**로 줄었고, 요청
  개수도 CSS 13개(+인라인 JS 1개) → 2개(`app.js` + `styles.min.css`)로
  줄었습니다.

**참고로 안 한 것 (정직하게 밝혀둡니다):**

- **JS 코드 자체의 압축(minify)은 기본값으로는 안 되어 있습니다.** 이 앱은 화면을
  그릴 때 여러 줄짜리 템플릿 문자열(백틱) 안에 HTML/SVG를 그대로 넣는 방식을
  아주 많이 쓰는데, 이런 코드를 안전하게 압축하려면 실제 JS 문법을 완전히
  이해하는 전문 도구(terser)가 필요합니다. 아래 "JS 압축(선택 사항)" 항목에
  설치 방법을 적어뒀어요 — 설치하면 `build.js`가 자동으로 감지해서 압축하고,
  설치하지 않으면 지금처럼 압축 없이 그대로 동작합니다(둘 다 안전합니다).
- **화면(페이지)별로 JS를 나눠서 필요할 때만 불러오는, 진짜 의미의 "코드
  스플리팅"도 하지 않았습니다.** 지금 구조는 모든 화면의 함수가 하나의 공유
  스코프 안에서 서로를 직접 호출하는 방식이라, 이걸 화면별로 진짜 분리하려면
  ES 모듈(import/export) 구조로 앱을 다시 짜야 합니다. 브라우저에서 실제로
  띄워보면서 검증할 방법이 없는 지금 이 환경에서 그 정도의 구조 변경을 하는
  건 위험 부담이 너무 커서, 이번에는 지금 한 것(번들 분리 + CSS 압축)까지만
  안전하게 진행했습니다.

## JS 압축(선택 사항): terser 설치하기

지금 그대로 써도 전혀 문제없습니다 — terser가 없으면 `build.js`가 압축 없이
`app.js`를 만들 뿐, 에러가 나지 않습니다. 용량을 조금이라도 더 줄이고 싶을 때만
아래를 하시면 됩니다.

1. Node.js가 설치된 컴퓨터에서 이 프로젝트 폴더로 들어갑니다.
2. 아래 명령을 **한 번만** 실행해서 terser를 설치합니다.
   ```
   npm install
   ```
3. 평소처럼 빌드합니다.
   ```
   node build.js
   ```
   (또는 `npm run build`)
4. 터미널에 `JS 압축: 함 (…KB → …KB, …% 감소)`라고 뜨면 성공입니다. 이 문구가
   그대로 `JS 압축: 안 함`이라고 뜬다면 terser 설치가 안 된 것이니 2번부터
   다시 해보세요.

**압축을 켠 뒤에는 꼭 한 번 실제로 써보고 확인해주세요.** 저는 지금 이 작업
환경에서 네트워크가 막혀 있어 terser를 직접 설치해서 실제로 압축된 결과물을
브라우저에서 띄워보는 것까지는 확인하지 못했습니다(그래서 기본값은 압축 없이
두었습니다). terser 자체는 전 세계적으로 아주 널리 쓰이는 검증된 도구지만,
로그인 → 데이터 저장 → 새로고침 → 백업/복원 정도는 압축 켠 뒤에 한 번 훑어봐
주시면 안심하고 쓰실 수 있어요. 혹시 압축 후 뭔가 이상하게 동작하면
`node_modules`와 `package-lock.json`을 지우고 terser 없이(`npm install` 하지
않은 상태로) 다시 빌드하면 바로 이전의 안전한 상태로 돌아갑니다.
